# Архитектура 0.2

`agent-core` — Java-ядро без Spring: immutable OpenAPI-каталог, NetworkNT JSON Schema, протокол диалога, адаптер модели, HTTP-исполнитель и интерфейс SessionStore. Spring starter предоставляет контроллер и конфигурацию. React отображает подтверждения и результаты. Доменные сущности в ядре отсутствуют.

## Обработка

1. Хост аутентифицирует запрос. Контроллер получает владельца только из Principal.
2. JDBC проверяет квоту и сохраняет PLANNING, аннулируя предыдущее подтверждение.
3. Модель выбирает одну разрешённую операцию. При большом каталоге выбор и заполнение схемы разделены на два вызова. Bearer-токен и ответы бизнес-API ей не передаются.
4. Детерминированная проверка схемы возвращает ошибки либо READY_FOR_CONFIRMATION. Defaults автоматически не подставляются, неизвестные ID не выдумываются.
5. Кнопка подтверждает только сохранённые данные и версию контракта. Все запросы, включая GET, требуют подтверждения.
6. Короткая SQL-транзакция CAS переводит READY в EXECUTING. Только победивший экземпляр отправляет HTTP-запрос. Во время внешних вызовов транзакция и блокировка БД не удерживаются.
7. HTTP-статус и безопасная проекция ответа сохраняются вместе с audit. Повтор подтверждения читает сохранённое состояние.

Состояние: IDLE → PLANNING → COLLECTING_FIELDS / READY_FOR_CONFIRMATION → EXECUTING → DONE / FAILED / UNKNOWN. Отмена и истечение времени аннулируют подтверждение. Новый текст после завершения начинает новое предложение. Через 120 секунд зависший PLANNING разрешает повтор подготовки, EXECUTING становится UNKNOWN без повторного HTTP-вызова.

## Хранение и ограничения

- PostgreSQL / H2, optimistic revision CAS; admission-lock только для коротких операций создания и квот. Для высокой нагрузки требуется измерение конкуренции этого lock.
- Payload сессии шифруется AES-GCM, AAD содержит session ID. Индекс владельца — HMAC. Ключ один для всех реплик, хранится отдельно от БД. Автоматической ротации ключей нет.
- В audit только session/operation/confirmation IDs, HMAC владельца, время, состояние и HTTP-код. Audit не означает, что бизнес-транзакция точно завершилась. TTL 30 дней.
- Session TTL 24 часа, confirmation TTL 3 минуты; cleanup каждую минуту. Просроченные сессии недоступны сразу. Квота команд 20/минуту, статусов 60/минуту по умолчанию.
- Максимумы: OpenAPI 4 MB, текст 8000 символов, arguments 32000 символов, ответ модели 128 KB, ответ REST 512 KiB. Проекция ответа до 50 строк, текстовое поле до 2000 символов.
- Origin backend фиксирован конфигурацией. OpenAPI servers игнорируется. Редиректы отключены. Параметры пути ограничены буквами, цифрами, `_`, `-`; query URL-encoded. Заголовки и URL модель не выбирает.
- Запрос к модели: до двух вызовов по 25 секунд; бизнес-API 20 секунд. Ни один из адаптеров не повторяет запрос автоматически.

## Контракт

Полный OpenAPI хранится в ресурсах и кэшируется при старте, без runtime сетевой загрузки. Каждая доступная операция компилируется один раз. Поддерживаемый профиль описан в [README](../../README.md). Источник спецификации должен быть доверенным; schema complexity и Java regex не являются песочницей для загруженных пользователем схем.

Rental Management генерирует контракт из контроллеров, DTO и Bean Validation через springdoc. Дополнительные аннотации email/непустых строк/неотрицательных чисел переносятся из тех же Java-полей, а не дублируются вручную. Тест проверяет все mapping, уникальные operation IDs и отсутствие расхождения snapshot. Обновление API требует регенерации и review политики x-agent-enabled.

Полный каталог включает 66 операций, 19 разрешены агенту. PUT пока отключён: API заменяет поля, поэтому перед его включением нужны чтение текущего объекта и защита от конкурентного изменения. DELETE и чувствительные маршруты требуют отдельной политики. Полный каталог не означает право агента выполнять любой endpoint.

## Граница гарантий

CAS обеспечивает не более одной отправки одного confirmation ID, но не распределённую exactly-once транзакцию. При сбое между записью EXECUTING и HTTP-вызовом команда может вообще не уйти; после сбоя между бизнес-транзакцией и записью DONE команда могла завершиться. Обе ситуации требуют проверки результата, а не автоматического retry. Rental Management пока не обрабатывает Idempotency-Key транзакционно.

Текущее решение использует права пользователя. Бизнес-API обязательно повторно проверяет ownership и доменные правила; валидация OpenAPI этого не заменяет. Scoped agent tokens, серверная идемпотентность, поиск сущностей по имени, нагрузочные SLA и оценка качества языка остаются отдельными задачами. Маскирование для облака и голос отложены владельцем.
